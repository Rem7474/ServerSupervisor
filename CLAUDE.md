# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

### Local dev stack
```bash
docker compose up postgres          # PostgreSQL only
cd server && go run ./cmd/server    # API server on :8080
cd frontend && npm run dev          # Vite dev server on :3000 (proxies /api → :8080)
```

### Build
```bash
cd server   && go build ./...
cd agent    && bash build.sh v1.0.0   # multi-arch: amd64/arm64/armv7/armv6
cd frontend && npm run build
```

### Test & lint
```bash
cd server   && go test -v -race ./... && golangci-lint run   # v2.12.2, blocking in CI (server/.golangci.yml)
cd agent    && go test -v -race -coverprofile=coverage.out ./... && golangci-lint run   # agent/.golangci.yml
cd frontend && npm run typecheck && npm run lint
```

CI also blocks on `go mod tidy` cleanliness (both Go modules) and on `frontend/src/types/generated.ts` staying in sync with the Go models (`ci-server.yml` regenerates and diffs it) — see the generated-types note below before changing a model.

## Architecture

Three independent Go/Vue modules: **server** (Go API), **agent** (Go collector), **frontend** (Vue 3 SPA).

### Server (`server/`)

- Entry point: [cmd/server/main.go](server/cmd/server/main.go) — loads config, validates strict secrets, runs DB migrations, starts background goroutines + pollers, serves HTTP, handles graceful shutdown.
- [internal/api/router.go](server/internal/api/router.go) — only routes/middleware wiring. `SetupRouter(db, cfg, notifHub, bus, sched, dispatcher)` returns `(*gin.Engine, *ReleaseTrackerHandler, *ProxmoxHandler, *NPMHandler, cleanup func())` — the handlers whose pollers main starts, plus a cleanup fn that must be called on shutdown to stop the rate-limiter goroutines. `bus` is the [internal/events](server/internal/events/) pub/sub bus, threaded into the WS handler + the writer services so snapshots are pushed on write.
- [internal/api/middleware.go](server/internal/api/middleware.go) — JWT / CSRF / WS-token / rate limiter / API-key middlewares (CORS, security headers, request logger). WebSocket auth is cookie-first with an in-band `{"type":"auth","token":...}` JSON message fallback — the `?token=` query-string fallback was deliberately removed (it leaked into proxy/browser history logs); don't reintroduce it. `IPRateLimiter` is an in-process `map[string]*rate.Limiter` — **per-instance only, no shared state**. This is intentional and consistent with the rest of the server (the `internal/events` bus, the WS dashboard cache and every WS hub are equally in-process/single-instance), not an oversight to patch in isolation. If horizontal scaling of the server is ever needed, the rate limiter, the event bus and the WS hubs would all need to move to a shared backend (e.g. Redis pub/sub) together — swapping only the rate limiter would leave the rest broken under multi-instance while adding a new hard dependency for no coherent gain. Today's deployment model (`docker-compose.yml`) runs exactly one `server` container, so this does not apply yet.
- [internal/handlers/](server/internal/handlers/) — one or more files per domain (auth, hosts, agent, docker, apt, proxmox*, alert_rules, web_logs, ssl, uptime, …). Handlers translate HTTP; `respondError(c, err)` ([httperr.go](server/internal/handlers/httperr.go)) renders typed [apperr](server/internal/apperr/) errors uniformly. Background scheduling is **not** owned by handlers — they expose a poll-once op (`ProxmoxHandler.PollOnce`, `ReleaseTrackerHandler.CheckAll`) + `SetBackgroundContext(ctx)`, and [poller.Every](server/internal/poller/poller.go) (started from main) owns the loop.
- [internal/services/](server/internal/services/) — application/service layer, **one package per domain** (agent, alertrule, apt, audit, authn, backup, dashboard, discovery, docker, dockerversions, gitwebhook, host, hostperm, maintenance, network, notifications, notifychannels, npm, proxmox, push, releasetracker, runbook, scheduledtask, settings, ssl, uptime, user, weblogs). Each owns its business logic behind a consumer-defined `Repository` port (satisfied structurally by `*database.DB`), so it is unit-testable without a database. **Every HTTP domain is migrated** — handlers are thin translators (bind → call service → `respondError`); the only `*database.DB` a handler still holds is for `requireHostAccess` ([host_authz.go](server/internal/handlers/host_authz.go)), the per-host authz guard that needs `*gin.Context`. Cross-package collaborators that need the concrete `*DB` (alert-engine preview, network snapshot builder, the relocated proxmox/release-tracker background pollers) are injected as funcs or hold `*DB` directly for background sync.
- [internal/events/](server/internal/events/) — tiny in-process pub/sub bus (zero deps → no import cycles, nil-safe) that drives the event-driven WS snapshots. Writers `Publish(topic)` after a state change; WS connections subscribe. See the `internal/ws` bullet.
- [internal/apperr/](server/internal/apperr/) — typed domain errors (`NotFound`/`Validation`/`Conflict`/`Forbidden`/`Unauthorized`/`TooManyRequests`/`BadGateway`/`Failed`/`Internal`) with a machine `Code` + HTTP status; `From()` coerces any error. `Internal` hides the message (generic 500); `Failed` keeps a human 500 message. Rendered as `{"error","code"}` by `respondError` at **every** handler error site.
- [internal/safego/](server/internal/safego/) — shared `Go` / `Recover` / `RecoverErr` helper: recovers a panic, logs it with a stack trace, and lets the process keep running. **Every detached goroutine** (pollers, WS fan-out, background jobs, notification dispatch) must go through it instead of a raw `go func(){...}()` — Go doesn't let a sibling goroutine recover another's panic, so an unprotected one takes down the whole server.
- [internal/poller/](server/internal/poller/) — generic `Every(ctx, interval, immediate, name, tick)` scheduling loop (wraps each tick in `safego`); stops on ctx cancellation.
- [internal/database/db.go](server/internal/database/db.go) — DB connection + embedded migration runner (`migrations/*.sql`). Migrations run in filename order on every startup; `schema_migrations` tracks applied ones. `000_full_baseline_breaking.sql` is the consolidated baseline (a `pg_dump --schema-only` of a DB migrated through 063). It records the migrations it subsumes with a plain `INSERT INTO schema_migrations (filename) VALUES (...)` listing `001..063` at the end of the file, so they never re-run. [migrations_baseline.go](server/internal/database/migrations_baseline.go)'s `readBaselineManifest` looks for `-- ===== BEGIN <file>.sql =====` markers instead — the current baseline has none, so it returns an empty set and pre-marks nothing. Harmless today (files `001..063` no longer ship, and the `INSERT` covers them), but don't rely on that marker mechanism: it describes a baseline format this repo no longer uses.
- [internal/database/db_*.go](server/internal/database/) — DB methods split by domain (~40 files). **All DB methods take `context.Context` as first arg.** Use `c.Request.Context()` from handlers; `context.Background()` only for background goroutines.
- [internal/models/](server/internal/models/) — shared structs **split per domain file** (alert.go, auth.go, command.go, docker.go, host.go, network.go, npm.go, proxmox.go, report.go, settings.go, synthetic.go, task.go, tracker.go, user.go, web_logs.go, webhook.go, ws.go). There is **no single `models.go`**.
- [internal/config/config.go](server/internal/config/config.go) — config loaded from env vars then overridden by `settings` table via `OverrideFromDB()`. The `DBSettingsLoader` interface avoids the database→config import cycle.
- [internal/alerts/](server/internal/alerts/) — evaluates alert rules and dispatches notifications, split into `engine.go` (orchestration) / `metrics.go` (metric resolvers) / `authfailures.go` (Proxmox syslog auth-failure parsing) / `severity.go` (hysteresis) / `notify.go` (dispatch). The exported entry points (`GetMetricValue`, `MatchRule`, `BuildDockerTestTargets`, `FetchProxmoxAuthFailureLogs`, `ResolveStaleIncidentsForRule`, `CurrentIncidentValue`) are injected into the alertrule/notifications services as funcs.
- [internal/ws/](server/internal/ws/) — `WSHandler` (per-page WebSocket endpoints), `CommandStreamHub` (live command output), `NotificationHub` (push-on-fire notifications). WS routes: `dashboard / hosts/:id / docker / network / apt / commands/stream/:id / notifications`. The snapshot endpoints (dashboard/host/docker/network/apt) are **event-driven**: each connection subscribes to its topic(s) on the [internal/events](server/internal/events/) bus and rebuilds+pushes (debounced ~750ms, diff-hash suppressed) when a writer publishes — agent ingest, the proxmox poller, the host-status monitor and apt command results all publish. A slow `snapshotSafetyInterval` (60s) rebuild is only a self-healing backstop, not the primary refresh path.
- [internal/background/](server/internal/background/) — `bg.Add(...)` jobs: audit cleanup, host status monitor, alert eval, metrics retention (tracker tag digests only — raw metric retention is owned by TimescaleDB policies), web-logs retention, uptime worker, SSL worker.
- [internal/dispatch/](server/internal/dispatch/) — server-side helper that persists `remote_commands` rows used by handlers + alert engine to queue agent commands.
- [internal/proxmoxclient/](server/internal/proxmoxclient/) — PVE HTTP API client (PVEAPIToken auth, optional TLS skip-verify).
- [internal/releasetracker/](server/internal/releasetracker/) — pure version-comparison helpers (`NormalizeDigest`, `IsVersionUpToDate`, `ResolveContainerVersion`). **Does not contain a Tracker** — the active release-tracking (CRUD + poll→detect→dispatch→notify pipeline) lives in [internal/services/releasetracker](server/internal/services/releasetracker/), behind a thin `ReleaseTrackerHandler`.
- [internal/synthetic/](server/internal/synthetic/) — uptime probe runner (`http`/`tcp`/`icmp`, `UptimeProbe.Type`) + SSL certificate checker (run from background jobs). ICMP (`checkICMP`, ROADMAP.md item #8 — a generic ping check for equipment that isn't agent-installable and exposes no TCP/HTTP port) tries an unprivileged `udp4` "ping socket" first, falling back to a raw `ip4:icmp` socket, which needs `CAP_NET_RAW` — granted to the non-root server binary via `setcap` in `server/Dockerfile` rather than running the container as root (`CAP_NET_RAW` is already in Docker's default capability set, so no `cap_add` is needed unless a deployment hardens with `cap_drop: [ALL]`). A container that genuinely can't get either socket type reports the ICMP check as failed with an explicit "CAP_NET_RAW manquant" error rather than a false "down" — verified end-to-end against the real built image (setcap'd binary, non-root user) before landing, not just unit-tested. `checkICMP`'s socket/echo logic is factored out into an exported `PingICMP(ctx, target) (success bool, latencyMs int, err error)` so [internal/services/discovery](server/internal/services/discovery/) (ROADMAP.md item #12 — subnet ping-sweep discovery, `POST /api/v1/hosts/discover`) reuses the exact same CAP_NET_RAW-dependent path instead of re-implementing it; `discovery.Service.Scan` bounds a request to IPv4 `/24`–`/30` (2–254 addresses), pings each concurrently (a `sync.WaitGroup` + semaphore, same shape as the uptime worker's own probe fan-out), and cross-references responders against `host.Repository.GetAllHosts` to flag already-registered IPs. Discovered addresses are handed to a new `host.Service.RegisterBulk` / `POST /api/v1/hosts/bulk` (mirrors `releasetracker.Service.CreateBulk`'s per-entry independent-validation shape) so a batch of new hosts can be confirmed in one call, each still getting its own real API key back.
- [internal/gitprovider/](server/internal/gitprovider/) — GitHub / GitLab / Gitea release-API client (used by `ReleaseTrackerHandler`).
- [internal/scheduler/](server/internal/scheduler/) — cron-based `TaskScheduler` for scheduled-task executions.
- [internal/notify/](server/internal/notify/) — SMTP + ntfy senders + HTML alert email template.
- Smaller supporting packages, listed here so they aren't rediscovered as "undocumented": [internal/auth](server/internal/auth/) (TOTP generation/verification), [internal/cookies](server/internal/cookies/) (session cookie construction — `Secure` is forced by `cfg.TLSEnabled`, which is the *only* thing that env var does), [internal/errors](server/internal/errors/) (named error-code constants, distinct from `apperr`'s typed errors), [internal/logging](server/internal/logging/) (slog setup), [internal/networkview](server/internal/networkview/) (network snapshot + IP inventory builders), [internal/npmclient](server/internal/npmclient/) (Nginx Proxy Manager HTTP client), [internal/threatdetect](server/internal/threatdetect/) (web-log threat scoring, tuned by the `THREAT_*` env vars), [internal/testutil](server/internal/testutil/) (ephemeral Postgres via testcontainers).

### Agent (`agent/`)

- Entry point: [cmd/agent/main.go](agent/cmd/agent/main.go) — flag parsing, `--init` config generation, `--internal-update` self-update helper, main loop with sequential command worker.
- [internal/reporter/reporter.go](agent/internal/reporter/reporter.go) — collects metrics in parallel goroutines, builds `Report`, POSTs `/api/agent/report`, returns commands to the queue.
- [internal/dispatcher/](agent/internal/dispatcher/) — concurrent command runner with:
  - `dispatcher.go` — APT mutex + 4-slot semaphore for other modules + 45-min absolute timeout.
  - `registry.go` — module → handler map (`docker`, `compose`, `apt`, `journal`, `agent`, `systemd`, `processes`, `custom`, `crowdsec`, `restic`).
  - `handler_<module>.go` — one file per module.
- [internal/sender/sender.go](agent/internal/sender/sender.go) — `Report` / `PendingCommand` / `CommandResult` structs + HTTP client (`X-API-Key` header, two timeouts: 30s reports / 30min commands).
- [internal/collector/](agent/internal/collector/) — one file per domain (system, docker, apt, disk, web_logs, systemd, journal, processes, crowdsec, restic, network_flows + its L7 variant, compose_update, container_ips, diagnostics).
- [internal/config/tasks.go](agent/internal/config/tasks.go) — loads `tasks.yaml` (custom task definitions: id/command/timeout/env).

### Frontend (`frontend/src/`)

- [api/client.ts](frontend/src/api/client.ts) — shared Axios instance (`baseURL: /api`, `withCredentials: true`) + interceptors (CSRF double-submit via X-CSRF-Token, 401 → hard redirect to login). Endpoints live in per-domain modules (`auth.ts`, `hosts.ts`, `docker.ts`, `proxmox.ts`, `npm.ts`, `uptime.ts`, `ssl.ts`, …); [api/index.ts](frontend/src/api/index.ts) is a thin barrel that spreads them into one default export. **Add new endpoints to the relevant domain module, never to `index.ts`.**
- [router/index.ts](frontend/src/router/index.ts) — all routes use dynamic `import()` for lazy loading + chunk-retry logic on `ChunkLoadError`.
- [stores/](frontend/src/stores/) — Pinia (`auth`, `hosts`, `alertRules`, `dashboard`).
- [views/](frontend/src/views/) — one per route.
- [components/](frontend/src/components/) — organised by domain (alerts/, apt/, common/, dashboard/, disk/, docker/, host/, monitoring/, network/, network-flows/, proxmox/, security/, settings/, webhooks/) + a flat layer of generic components.
- [composables/](frontend/src/composables/) — `useWebSocket`, `useCommandStream`, `useDashboard`, `useHostDetail`, `useFormValidator`, `useToast`, `useConfirmDialog`, `usePagination`, …
- [utils/](frontend/src/utils/) — formatters, chart theme, dockerPorts, cron, dayjs, httpErrorBus, statusClasses, …

**TypeScript adoption**: all `.vue` files use `<script setup lang="ts">` (100% migrated). Composables, stores and `utils/` are `.ts`. The API + WebSocket payloads are fully typed against the generated models (see "Generated API types" below), including the dashboard / notification / IP-timeline consumers. One intentional residual remains: `useHostDetail.ts` keeps its 12 host-detail display refs as a local `AnyRecord` behind safe `asRecord`/`asRecordArray` coercers — the WS boundary feeding them is already typed (`WSHostSnapshot`), so this is a deliberate display-layer abstraction, not an unchecked wire contract. Typing it would cascade through the large `HostDetailView` + its sub-tabs for no contract-robustness gain.

### Agent ↔ Server protocol

Agents authenticate with a per-host API key sent in the `X-API-Key` header (cfg.APIKeyHeader). Keys are bcrypt-hashed at rest; agents are looked up via `db.GetHostByAPIKey`.

| Direction | Endpoint | Purpose |
|---|---|---|
| Agent → Server | `POST /api/agent/report` | Metrics, Docker state, APT status, web logs, disk health, capabilities |
| Server → Agent | Response body of `/report` | `{commands: []PendingCommand{ID, Module, Action, Target, Payload}, skip_metrics: bool}` |
| Agent → Server | `POST /api/agent/command/result` | `CommandResult{CommandID, Status, Output, AptStatus}` |
| Agent → Server | `POST /api/agent/command/stream` | Streaming chunk output for long commands |
| Agent → Server | `POST /api/agent/audit` | Autonomous actions (e.g. apt update on start) |
| Agent → Server | `POST /api/agent/restic-status` | Out-of-band Restic status push after a `run_backup` command completes (mirrors `apt-status`) |
| Agent ↔ Server | `GET /api/agent/ws` (optional) | Low-latency command push — see below |

Commands persist in `remote_commands` (UUID PK, `module`, `action`, `target`, `payload` JSONB, `status`, `audit_log_id` FK to audit_logs ON DELETE SET NULL). Live command output streams over WebSocket at `GET /api/v1/ws/commands/stream/:id` (hub in [ws/command_stream.go](server/internal/ws/command_stream.go)).

`GET /api/agent/ws` ([ws/agent_hub.go](server/internal/ws/agent_hub.go), agent side [agentws/client.go](agent/internal/agentws/client.go)) is a purely additive, agent-initiated WebSocket the agent opens (authenticated the same way as every other `/api/agent/*` call, via `X-API-Key` on the upgrade request) to be nudged the instant a command is dispatched, instead of waiting out `report_interval`. It deliberately carries no command content — the server pushes only `{"type":"poll_now"}`, which triggers the agent's existing report/poll cycle sooner; the agent's `POST /report` claim query is already atomic (`FOR UPDATE SKIP LOCKED`), so a second delivery path carrying actual command data would race it and risk double execution. `dispatch.Dispatcher` holds this as an optional `AgentPusher` interface (`Notify(hostID) bool`, wired post-construction via `SetAgentPusher` — `*ws.AgentHub` satisfies it structurally, no import cycle) so an agent with no live connection — an older binary, or one behind a proxy that blocks WS upgrades — is unaffected and keeps working exactly as before via the regular poll. Toggle: agent's `disable_ws_push` config key (default `false` = enabled).

The agent `Report` struct (`agent/internal/sender`) is fully typed against `agent/internal/collector` types; the server deserialises the same JSON into the strongly-typed `models.AgentReport`. The two modules share no code, so a **golden-fixture contract test** guards the wire format against silent drift: `protocol/agent_report.golden.json` is regenerated by the agent (`TestReportContractGolden`, reflection-filled) and decoded by the server with `DisallowUnknownFields` (`TestAgentReportContract`). When adding/renaming a report field, update both struct sets, regenerate the golden (`cd agent && go test ./internal/sender -run TestReportContractGolden -update`), and re-run the server test. See [protocol/README.md](protocol/README.md).

### Alert rules

Rules have a single `actions JSONB` column: `{channels: ["smtp","ntfy","browser","notify"], smtp_to, ntfy_topic, cooldown, escalate_after_minutes, command_trigger}`. The engine in `alerts/engine.go` iterates `rule.Actions.Channels` to dispatch. `source_type` is one of `agent | proxmox | synthetic`. Hysteresis: `threshold_warn / threshold_crit / threshold_clear_warn / threshold_clear_crit` per severity.

An open incident can be acknowledged (`POST /alerts/incidents/:id/ack`, admin-only like `resolve` — see `AlertRulesHandler.AcknowledgeIncident`'s doc comment for why ack isn't scoped to Operator+ the way host-scoped domains are) — `alert_incidents.acknowledged_at`/`acknowledged_by`, orthogonal to `resolved_at` (an incident can be open+acknowledged, open+unacknowledged, or resolved; ack no longer matters once resolved). `AlertActions.EscalateAfterMinutes`, when > 0, re-sends the fired notification for an open, unacknowledged incident every N minutes since it last notified (`alert_incidents.last_escalated_at`) — `maybeEscalateIncident` in `alerts/engine.go`, checked in the same per-target loop as the maintenance-window branch below it. Escalation never re-dispatches `command_trigger` (repeating a remediation command on a timer is a materially different, riskier action than repeating a notification).

A newly-firing incident whose target resolves to a host that's currently down (an open `status_offline`/`heartbeat_timeout` incident on that same host) gets linked via `alert_incidents.correlated_with` to that host-down incident instead of sending its own notification — `correlationTargetIncidentID`/`correlationHostID` in `alerts/engine.go`, checked right before the newly-created-incident notify path. This is the fix for a host going offline cascading into one independent notification per Docker container/rule on it. `correlationHostID` resolves `docker:container:`/`docker:compose:`/confirmed-link `proxmox:guest:` targets back to their real host (same three shapes `triggerAlertCommand` resolves, kept as a separate small function rather than a shared refactor to avoid touching that already-working path); non-guest Proxmox scopes and synthetic probes have no single owning host and are never correlated. Scope is deliberately narrow — this suppresses the concrete "host down → N child alerts" cascade, not a general cross-rule correlation engine. A correlated incident is still fully recorded (visible in the UI, an `IconLink` marker in `AlertIncidentList.vue`) and never independently escalates either (`maybeEscalateIncident` checks `CorrelatedWith`) — only its own loud notification and `command_trigger` are suppressed. Computed once at creation time, not re-evaluated if the host-down incident later resolves first.

`alert_rule_templates` (`internal/services/alertrule/templates.go`, same package as rule CRUD so it can reuse `validateAlertRuleMetricOperator`/`validateAlertActions`/`Service.Create` directly) is a host-agnostic rule "recipe" — name/metric/operator/thresholds/actions, no `host_id`. `POST /alert-rule-templates/:id/apply` (`host_ids: []string`) stamps out one independent `alert_rules` row per host via the exact same `Create` path a manual single-host rule goes through — not a live link: editing or deleting a template never touches rules already created from it, and applying is not all-or-nothing (`ApplyAlertRuleTemplateResult.Errors` is keyed by host, one host's failure doesn't block the rest). Deliberately agent-metrics-only (`isTemplatableMetric`) — Docker scope requires a `host_id` per rule and Proxmox scope is cluster-level already, so neither fits "apply the same recipe to N hosts"; the two synthetic metrics (`uptime_down_count`/`ssl_min_days_remaining`) evaluate globally once per rule, not per host, so they're excluded too. Frontend: `AlertsView.vue`'s "Modèles" tab (`AlertRuleTemplateList.vue` + `AlertRuleTemplateModal.vue` + `AlertRuleTemplateApplyModal.vue`, host picker filterable by name or `Host.Tags`) — applying refetches `useAlertRulesStore` explicitly since the "Règles" tab's rule list has no other way to learn about rules created outside its own CRUD path.

### Maintenance windows

`maintenance_windows` (`internal/services/maintenance`) suppresses alert notifications for a time range: scoped to one host (`host_id` set, Operator+ on that host to create/delete, same `requireHostAccess` shape as scheduled tasks) or every host at once (`host_id` NULL, a global window, admin-only — it silences the entire system). The engine checks `db.IsHostInMaintenance` once per evaluation target, right where the disabled-rule short-circuit already lives (`alerts/engine.go`): a covered target skips evaluation entirely (no new incident) and any already-open incident is resolved silently — the lightweight incident-list refresh ping still fires, but no loud channel (smtp/ntfy/push/browser) or `command_trigger`, so a planned intervention produces zero alert noise in either direction. A synthetic evaluation target (`proxmox:*`/`docker:*`/`synthetic:*`, none of which exist in `hosts`) can only ever match a global window, never a host-scoped one — same trade-off `resolvableHostID` already makes for host-permission scoping (see host_authz.go above); resolving a Proxmox guest or Docker container back to its real host for maintenance purposes isn't implemented.

### Audit logs

`audit_logs` (distinct from `login_events`, which covers connection events only) rows get a `category` computed once at write time by `models.CategorizeAuditAction` and stored, not re-derived on read — `action` is free text with no enum (any `CreateAuditLog` caller can pass a new string), so categorization buckets a handful of known prefixes/exact matches (`alert_*` → `alert`, `unblock_ip` → `auth`, `update_settings`/`cleanup_*` → `settings`) and defaults everything else — the large "an operation was dispatched or executed" set (`apt_*`/`docker_*`/`journalctl`/`webhook_trigger`/`agent_update`/...) — to `command`. `models.AuditCategories()` is the single source of truth for the category list (key + French label), surfaced to the frontend via the `/settings` snapshot's `auditCategories` field rather than duplicated client-side. Retention: the hourly `audit-cleanup` background job (`internal/background/audit.go`) purges per category — `cfg.AuditRetentionDaysByCategory[category]` if set (settings-only, JSON-encoded under key `audit_retention_days_by_category`, no env var — a per-category map doesn't fit the flat `KEY=value` env shape), else `cfg.AuditRetentionDays`/`AUDIT_RETENTION_DAYS`. `GET /v1/audit/logs` and `/audit/logs/export` (CSV, capped at 20 000 rows) share the same `category`/`from`/`to` filters (`database.AuditLogFilter`). Frontend: `AuditLogsView.vue`'s "Journal" tab (raw `audit_logs` browser — the pre-existing "Commandes"/"Connexions" tabs cover `remote_commands`/`login_events` instead, not this table) and `SettingsRetentionCard.vue`'s per-category inputs.

### Authentication / MFA

`internal/services/authn` covers credentials, sessions and both second-factor methods a user can register: TOTP (`totp_secret`/`backup_codes` columns on `users`, unchanged since before this feature) and WebAuthn (passkeys/security keys, `webauthn_credentials` table — [internal/services/authn/webauthn.go](server/internal/services/authn/webauthn.go)). `Authenticate()` treats either as sufficient to require the MFA step (`models.MFARequirement{TOTP, WebAuthn}` tells the frontend which button/field to offer); a user can have both, either, or neither. WebAuthn login is a **separate** ceremony (`BeginWebAuthnLogin`/`FinishWebAuthnLogin`, public routes since no session exists yet) rather than a code funneled through `Authenticate()` alongside `totp_code` — `BeginWebAuthnLogin` re-verifies the password itself (same brute-force/IP-block posture as the TOTP path) because there's no other proof the caller is who they claim before a challenge is issued. Registration/login challenges live in an in-process `webauthnSessionStore` (single-use, 5-minute TTL) — same one-instance-only tradeoff as the IP rate limiter and the WS hubs (see the server section above), not a design gap. The Relying Party ID/origins default to `BASE_URL`/`ALLOWED_ORIGINS` (`WEBAUTHN_RP_ID`/`WEBAUTHN_RP_ORIGINS` override for setups where the frontend truly isn't served from the API's own origin) — see `.env.example`.

### Proxmox integration

`SetupRouter` returns the `ProxmoxHandler` so `main.go` can `StartPoller()` it (30s tick by default, respects per-connection `poll_interval_sec`). Token secrets are stored in `proxmox_connections.token_secret` and never returned to the frontend; retrieved only by poller/test via `GetProxmoxTokenSecret()`.

Guest ↔ host links live in `proxmox_guest_links` with `status: suggested|confirmed|ignored` and `metrics_source: auto|agent|proxmox`. When `metrics_source = proxmox` and Proxmox data is fresh, the server signals `skip_metrics: true` to the agent so it stops sending CPU/RAM. Sensor-source-providing hosts (cpu_temperature / fan_rpm) keep sending metrics regardless.

Write actions against a live PVE cluster follow two different authorization postures, by design, not oversight: `MigrateGuest` and `NodeServiceAction` (systemd services on a node) are reachable by any authenticated user, gated only by the PVE API token's own `Sys.Modify` scope — the app trusts whatever the operator configured that token to allow. `GuestAction` (start/shutdown/reboot on a VM/CT, `services/proxmox/service.go`) is instead gated at the app layer too (`AdminOnlyMiddleware`, alongside connection management) because it can power off a running guest directly rather than requiring a second condition (a misconfigured service/migration target) to cause damage; it also deliberately excludes the hard "stop" (immediate power-off, no ACPI shutdown) from its action whitelist. Don't use `GuestAction`'s stricter gating as a template for future Proxmox write endpoints without checking which posture actually fits — most existing ones intentionally don't have it.

**Interactive LXC console** (`GET /api/v1/ws/proxmox/console/:guest_id`, `ws.WSHandler.ProxmoxConsole`) proxies a live shell (xterm.js ↔ PVE termproxy) over one bidirectional WebSocket. Follows `GuestAction`'s stricter posture (`AdminOnlyMiddleware`-equivalent role check, since a console session's blast radius is at least as large) and is the **first Proxmox write path to write an `audit_logs` row** (`proxmox_console_open`) — every other Proxmox action (`GuestAction`/`MigrateGuest`/`NodeServiceAction`) still doesn't audit. LXC only in V1; QEMU needs VNC/RFB instead of termproxy, a different wire protocol (ROADMAP.md items #27/#28, under "Hors audit initial").

PVE's `vncwebsocket` upgrade endpoint (shared by termproxy and VNC) does **not** accept `PVEAPIToken` auth — confirmed by a Proxmox staff forum reply, not assumed — so `proxmox_connections` carries an optional second credential pair (`pve_username`/`pve_password`, same "empty on update = keep existing" semantics as `token_secret`) used only to obtain a `PVEAuthCookie` via `POST /access/ticket` (`proxmoxclient.Client.login`) right before dialing the console socket; the API token still authenticates every other PVE call. The PVE user needs the `VM.Console` privilege. The termproxy wire protocol itself (`user:ticket\n` login handshake + `"OK"` ack, then `0:LEN:DATA`/`1:COLS:ROWS:`/`2` client-to-server framing with raw unframed server-to-client bytes) is undocumented in PVE's API viewer — implemented in `proxmoxclient.TermSession` against Proxmox's own `pve-xtermjs` source, not guessed. That framing is entirely internal to `TermSession`: the browser↔server leg speaks plain bytes for keystrokes/output plus one JSON control message for resize (`models.WSConsoleResize`), so the frontend never needs to know PVE's protocol exists.

### Release trackers + Git webhooks

- **Ambient Docker image-version engine** ([internal/services/dockerversions](server/internal/services/dockerversions/)) — the single place in the server that asks an OCI registry "what is the latest digest for image X, tag Y". It refreshes the `docker_image_versions` cache table on a slow ticker (`DOCKER_IMAGE_POLL_INTERVAL`, default 6h — it scans the whole fleet, and registries rate limit per source IP; wired from main.go via `releaseTrackerH.RefreshDockerImageVersions`, which exposes the *same* service instance the tracker poller holds, so the two never duplicate a registry call) for every distinct `image:tag` running on any host, plus the refs named by enabled docker trackers so a tracker whose container is stopped keeps working. Registry access itself still lives in [internal/gitprovider](server/internal/gitprovider/) (GHCR / Docker Hub / any `WWW-Authenticate`-discoverable v2 registry) — this package owns *when* those calls happen and *what* is cached. Private registries are matched best-effort against a stored `RegistryCredential` by registry host (`sameRegistryHost` normalizes `docker.io`/`index.docker.io`/`registry-1.docker.io`); no match leaves that image an explicit "unknown" with the reason recorded on the row, never a failed sweep, and a failed check keeps the last known good digest rather than blanking it. Two consumers read the cache and nothing else calls a registry: `ws.buildVersionComparisons` (a version badge for **every** container, tracked or not — tracker rows are emitted exactly as before, plus one ambient row per running `(host, image, tag)` group no tracker covers; the `up_to_date`/`update_available`/`unknown` verdict is computed server-side in `VersionComparison.Status` rather than re-derived in each Docker table's template) and `releasetracker.Poller.checkOneDocker` (detection/dispatch/notify only). `Service.Latest` refreshes a single ref on demand when its row is missing or older than one interval, so "vérifier maintenant" on a tracker is immediate without a second registry code path.
- `release_trackers` table: monitors GitHub/GitLab/Gitea releases **or** Docker registry digests. Detects new versions, then either notifies only (monitor-only) or dispatches a `module=custom` agent command. Handler: [handlers/release_trackers.go](server/internal/handlers/release_trackers.go). Background poller managed by `releaseTrackerH.StartPoller()`.
- A docker tracker is configured by **picking a running container** (host + container, `GET /release-trackers/pickable-containers` → `db.ListPickableContainers`), not by typing an image reference: `docker_image`/`docker_tag` are still stored (the update action must know exactly what it targets) but are derived from the selection. That picker is deliberately *not* `ListTrackableContainers`, which stays compose-label-restricted and tracker-less-only because it feeds the **bulk** flow (`TrackableContainersModal.vue`, now framed as "activer la mise à jour auto" since ambient visibility is automatic) where every created tracker auto-runs `compose pull`+`up -d` — only compose-owned containers can be safely auto-updated that way. The manual single-tracker picker has no such constraint (it only needs an image ref) and shows already-tracked containers flagged rather than hidden, so it can't be silently incomplete. A docker tracker may additionally name an **optional** git repo (`provider`/`repo_owner`/`repo_name`, previously git-only): purely to surface release notes — `Service.VersionHistory` keeps the digest history (`ListTrackerTagDigests`) as its spine and only borrows each matching release's title/URL/date from the provider (`enrichWithGitReleases`, best-effort: an unreachable repo never fails the history that already works without it).
- Compose-mode docker trackers (`update_action="compose"`) additionally support opt-in GitOps-style drift reconciliation via `reconcile_drift`: when the registry digest is unchanged (nothing new upstream) but the agent-reported *deployed* container digest no longer matches what the tracker last recorded (`db.TrackerDriftDetected`, comparing against `docker_containers.image_digest` — manual change, silent failure, ...), the poller (`Poller.reconcileComposeDrift`) either re-dispatches the same `compose_pull`+`up -d` to pull it back into line (`reconcile_drift=true`) or leaves it as a read-only `drift_detected` flag computed fresh on every `GET`/`LIST` (`reconcile_drift=false`, the default). Never pushes compose file content to the agent — same whitelisted `compose`/`update` dispatch every other path already uses.
- `git_webhooks` table: public HMAC-authenticated endpoint `POST /api/v1/webhooks/git/:id/receive` (no JWT, dedicated 5 req/s rate limiter) that triggers a `module=custom` agent command. SS_REPO_NAME / SS_BRANCH / SS_COMMIT_SHA / SS_COMMIT_MESSAGE / SS_PUSHER are injected into the subprocess env.

### Runbooks

`runbooks` / `runbook_steps` / `runbook_executions`: named, reusable sequences of dispatch steps (the same module/action/target/payload vocabulary already validated for `alert_rules`' `command_trigger` — see [internal/services/runbook](server/internal/services/runbook)). Each step names one host + an already-whitelisted agent-side action; nothing here can hand an agent a new capability (`agent/CLAUDE.md`'s "server can trigger a task by ID only" boundary applies). `POST /api/v1/runbooks/:id/run` dispatches only the first step; `runbook_execution_id` on `remote_commands` (mirrors `scheduled_task_id`'s existing shape) links each step's command back to its execution. Advancing to the next step — or terminating the execution as `completed`/`failed` — happens in `runbook.Service.NotifyComplete`, registered as an `agentsvc.CommandCompletionListener` alongside git webhooks and release trackers, so it fires whenever any command reaches a terminal state and no-ops for the (overwhelming majority of) commands that aren't runbook steps. A step whose `continue_on_failure` is false (the default) stops the whole execution on failure; the whole domain is admin-only in this MVP (a runbook can span the entire fleet in one dispatch, a bigger blast radius than a single scheduled task).

`scheduled_tasks`, by contrast, does **not** share that whitelist: `scheduledtask.Service`'s `validModules` (`internal/services/scheduledtask/service.go`) checks only that `module` is one of its known values — `action` is persisted unvalidated, trusting whatever the client sends. This is a real, existing asymmetry, not a bug papered over here: runbook/alert-rule steps can only ever name a server-enforced action, scheduled tasks can name anything the agent's module handler accepts. `components/DispatchStepEditor.vue` (frontend) — the shared host+module+action+target[+cron] form behind both Runbooks' step editor and Global Scheduled Tasks' create form — reflects this rather than hiding it: each caller passes its own `actionsForModule`/`targetConfig` functions (Runbooks' via `useRunbooks.ts`'s server-mirrored whitelist; Scheduled Tasks' via its own looser, advisory-only list with a free-text fallback for unlisted modules), so the UI's affordances match what each backend actually enforces. The module list itself (`utils/dispatchStep.ts`'s `DISPATCH_MODULES`) is shared by all three validators for the original six module keys, confirmed by reading each Go whitelist directly rather than assumed — `restic` is the one exception (see below): it's valid for `scheduled_tasks` only, so `GlobalScheduledTasksView.vue` passes `DispatchStepEditor` an extended `:modules` list rather than adding it to the shared `DISPATCH_MODULES`, which would have wrongly offered it to Runbooks/alert-rule command triggers too.

### Restic backups

Restic backup supervision — modeled after "Release trackers + Git webhooks" above, but without a public webhook (see below). Three layers:

- **Passive monitoring**: when `collect_restic: true`, the agent's periodic report includes a `restic` section (`agent/internal/collector/restic.go`'s `ResticStatus`) — read from a resticprofile JSON status-file if `restic_status_file_path` is configured, else a fallback of `restic snapshots --json`/`stats --json`. Stored server-side in `restic_status` (one row per host, upserted like `apt_status`).
- **Active trigger**: `POST /api/v1/hosts/:id/backup/run` (`internal/services/backup`) dispatches a `module=restic action=run_backup` agent command (`Target` = the resticprofile profile name, e.g. `files`/`db`) via the same `dispatch.Dispatcher` port every other domain uses, and creates a `running` row in `backup_runs`.
- **Recurring schedule**: reuses `scheduled_tasks` rather than a bespoke cron — `restic` was added to `scheduledtask.Service`'s `validModules`, so a nightly backup is just a scheduled task with `module=restic action=run_backup`.

Both trigger paths converge on `backup.Service.HandleCommandCompletion`, registered as an `agentsvc.CommandCompletionListener` alongside git webhooks/release trackers/runbooks: it looks up the terminal command, no-ops unless `module=restic action=run_backup`, then upserts `backup_runs` (update if `TriggerBackup` already created a `running` row, insert otherwise — the scheduled-task path never goes through `backup.Service` to create one upfront) from the JSON `ResticBackupSummary` the agent puts in `CommandResult.Output`. A failed run notifies via the shared `notifychannels.Dispatcher` (smtp/ntfy/browser/push), same as every other domain. A background job (`internal/background/backup_stall.go`) marks runs stuck `running` past a threshold (default 6h) as failed — there is no fixed absolute duration cap on a restic backup (see `agent/CLAUDE.md`'s dispatcher timeout exception), so a stalled agent connection is the only way a run gets stuck.

Live progress for a manually-triggered backup reuses the generic command-stream pipeline unmodified (`ws.CommandStreamHub` / `GET /api/v1/ws/commands/stream/:id` / frontend `useCommandStream()`) — the agent streams compact JSON progress events (`agent/internal/collector.ResticProgressEvent`) parsed from restic's own `--json` output, forced live via `RESTIC_PROGRESS_FPS` (restic disables progress output by default outside a TTY).

**No webhook.** An earlier design considered a `POST /api/backup/report` public endpoint for a cron *external* to ServerSupervisor to push a report directly (with a per-host token, mirroring `git_webhooks`' secret) — not implemented, since scheduling backups through `scheduled_tasks` covers the recurring case without a second auth surface. Revisit only if a host's backups are ever triggered outside ServerSupervisor's control entirely.

### Host exposure correlation (NPM ↔ web logs)

`GET /api/v1/hosts/:id/exposure` (viewer-level, same `HostPermissionMiddleware` group as the other per-host tabs) answers "which public domains actually route to this host, and what traffic/threats have hit them?" — a question the host detail page otherwise can't answer, because NPM's proxy-host config and the web-log rows it produces are both scoped to the *reverse-proxy* host's identity, not the backend's. `host.Service.Exposure` (in [internal/services/host](server/internal/services/host)) resolves the target host's own `ip_address`, then `db.GetHostExposure` ([db_host_exposure.go](server/internal/database/db_host_exposure.go)) joins `npm_proxy_hosts` on `forward_host = <that IP>` and aggregates `web_log_requests` for the resulting `domain_names` — by domain, not `host_id`, since the request rows were most likely collected by the agent tailing NPM's own access logs on a different host entirely. Compute-on-read, nothing persisted, same shape as `TrackerDriftDetected`. An empty IP short-circuits before querying (`npm_proxy_hosts.forward_host` defaults to `''`, and a blind match would false-positive against any not-yet-synced proxy host). Migration `076_web_log_requests_domain_index.sql` adds the `(domain, captured_at)` index this domain-first aggregate needs — the existing `web_log_requests` indexes are all host_id/source/ip-first.

### Web-logs dashboard performance (Traffic / Threats)

`GetWebLogsSummary` ([db_web_logs_summary.go](server/internal/database/db_web_logs_summary.go)) is the query behind the Traffic/Threats dashboards' main summary call. It fans out ~10 independent aggregate queries (traffic counts, top domains/endpoints/hosts, threats, CrowdSec) across goroutines joined with a `sync.WaitGroup` + a small `errCollector` (first error wins), instead of running them sequentially — same for the service-layer `Summary()` in [internal/services/weblogs](server/internal/services/weblogs), which parallelizes the summary/top-IP-geolocation/current-KPI/previous-KPI calls. This was a direct fix for the dashboard blowing its 30s HTTP timeout: the default "all hosts" view has no `host_id` filter, and every pre-existing index on `web_log_requests`/`web_log_snapshots` led with `host_id`/`source`/`ip`/`blocked`/`suspicious`, so a plain `captured_at >= $1` predicate forced a full sequential scan on each of those ~10+ queries. Migration `077_web_log_requests_captured_at_index.sql` adds the missing plain `(captured_at DESC)` index on both tables. The Traffic panel's auto-refresh also used to re-run the whole expensive summary+timeseries call every 8s; `useTraffic.ts` now polls the cheap indexed "live tail" (`GetWebLogsLive`) on that fast cadence and the heavy aggregate on a separate, much slower one (30s).

`/traffic` and `/threats` both route to `TrafficThreatsShell.vue` ([views](frontend/src/views)), a shared shell with a mode toggle (Vue d'ensemble / Menaces) that renders `TrafficOverviewPanel.vue` or `ThreatsPanel.vue` ([components/security](frontend/src/components/security)) — the two modes' bodies stayed genuinely distinct (different KPIs/charts/tables, backed by `useTraffic.ts`/`useBot.ts` respectively), so only the shell chrome (page header, mode toggle) and the source/host/search filter bar (`TrafficThreatsFilterBar.vue`) are actually shared, not the content. `MonitoringView.vue` took the opposite path: its uptime/SSL tabs were merged into one table (`components/monitoring/MonitoringOverviewPanel.vue`, backed by `useMonitoringOverview.ts`) instead of a shell+panel split, because — unlike Traffic/Threats — a probe and a cert can share a real identity (the NPM proxy host that created both via its monitoring toggle, `npm_proxy_host_id`), so one row can legitimately show both an uptime status and an SSL countdown side by side. `useMonitoringOverview.ts` composes `useUptimeProbes`/`useSslCertificates` (no fetch/CRUD logic duplicated) and adds only the merge-by-`npm_proxy_host_id`/sort/pagination layer on top; probes or certs with no NPM link (created manually) just render as their own single-metric row. Each NPM-linked row also has its own full detail page at `/monitoring/host/:id` ([views/MonitoringHostDetailView.vue](frontend/src/views/MonitoringHostDetailView.vue)) stacking both `UptimeDetailSection.vue`/`SslDetailSection.vue`; the standalone `/monitoring/probes/:id`/`/monitoring/ssl/:id` routes still exist for non-NPM-linked entities but redirect to the combined page if the loaded entity turns out to be NPM-linked, so every existing deep link (notifications, command palette, bookmarks) converges without needing every call site updated individually.

Domain/IP drill-down: `DomainDetailsModal.vue` and `IPTimelineModal.vue` ([components/security](frontend/src/components/security)) are shared between the two panels — a free-text search box in both modes (`looksLikeIP` in [utils/network.ts](frontend/src/utils/network.ts) picks the endpoint) opens the matching domain's or IP's full request breakdown even when it never made a "top N" list. `IPTimelineModal` takes a `read-only` prop that hides the CrowdSec ban action in Traffic mode (Threats mode keeps it, since incident response belongs there). This also fixed a broken link: the Threats panel's "most targeted hosts" table is keyed by vhost *domain name*, not a real `hosts.id` (see `fillWebLogsThreats`'s `most_targeted_hosts` — domain-scoped signal, not host-scoped, same conceptual gap the host-exposure feature above closes), so it now opens the domain modal instead of 404ing/500ing on a `/hosts/:id` route that was never a real host.

### Host detail / Proxmox node tab shell

`HostDetailView.vue` and `ProxmoxNodeView.vue` both render their tabs through `components/EntityTabShell.vue`: `tabs: EntityTab[]` (key/label/`badges[]`/`lazy`) + `v-model` for the active key, one named slot per tab key. `badges` is an array rather than a single value because Proxmox's "Tâches" tab needs two side by side (a total count plus a conditional failed-task warning). `lazy` (per tab, default off) controls mount timing: off mounts the slot content immediately behind `v-show` (Host's tabs — matches its pre-shell eager-mount-everything behavior); on defers to first activation and keeps it mounted after (Proxmox's tabs — matches its pre-shell `isTabMounted` behavior, now owned by the shell itself rather than the view's composable). The "visited" tracking watches the `modelValue` *prop*, not just its own click handler, so a tab switch driven externally (`ProxmoxNodeView`'s `load()` restoring the active tab from a `?tab=` query-string param) still marks that tab mounted. `cardHeader` toggles between Proxmox's `.card-header`-wrapped nav (nav sits inside a `.card`, tab content continues the same card) and Host's bare `.nav-tabs.mb-3` strip (nav sits directly in the page, each tab bringing its own card(s) below) — the one Tabler-specific concession the shell makes, consistent with this refonte's "style Tabler conservé" constraint.

Sharing stops at the shell. The two entities' tab *content* was evaluated pair by pair for a genuine data-model match (not just visual similarity) and none cleared that bar: Host's "Sécurité" is per-host RBAC (`hostPerms`, who can operate this host) against Proxmox's "Sécurité", a PVE syslog viewer (`ProxmoxNodeSecurityTab`, auth-failure/service log search) — unrelated domains despite the identical tab label. Host's systemd panel and Proxmox's "Services" tab both render a start/stop/restart table but pull from different backends with different field casing (agent-collected `active_state`/`sub_state` via command-dispatch-and-stream vs PVE's `active-state`/`sub-state`/`unit-state` via direct REST) and different action sets (Host's "Status" opens a live console stream with no Proxmox equivalent; Proxmox has "Reload" with no Host equivalent) — forcing a shared table would mean either a generic field-mapping/configurable-columns abstraction or dropping real functionality from one side. Host's APT tab (476 lines: install/upgrade actions, unattended-upgrades config and run history) and Proxmox's "Mises à jour" tab (84 lines, explicitly read-only — "pour appliquer les mises à jour, connectez-vous directement au nœud") differ in scope by design, not by gap. Host's command history (`remote_commands`: module/action/target/status) and Proxmox's task log (PVE's native UPID-based task queue: task_type/object_id/exit_status) are different backend concepts that only superficially resemble each other as "a list of past operations." Each tab stays specific to its own data source; nothing here is a placeholder for a future merge.

### Key env vars

`JWT_SECRET`, `ADMIN_PASSWORD`, `DB_PASSWORD` are required for any non-trivial run. See [.env.example](.env.example) for the full list. `APP_ENV=dev` bypasses strict-secret validation for local development. The `settings` table can override most runtime config after first boot.

## Conventions & pitfalls

- **Generated API types are a source of truth, not a suggestion.** [frontend/src/types/generated.ts](frontend/src/types/generated.ts) is generated from the Go domain models (`server/internal/models`) by [tygo](https://github.com/gzuidhof/tygo) (config: [server/tygo.yaml](server/tygo.yaml)). Whenever a Go model changes, regenerate with `npm run gen:types` (or `cd server && go run github.com/gzuidhof/tygo@v0.2.21 generate`) and commit the result — `ci-server.yml` regenerates it and fails the build if your commit doesn't match, so this isn't optional. Per-domain files in `frontend/src/types/` re-export the generated types and add what generation can't express (status unions, response envelopes, request-vs-response shapes) — see [frontend/src/types/README.md](frontend/src/types/README.md).
- **Migrations are forward-only** — no `Down()`, no rollback tooling (`server/internal/database/migrations/*.sql`, baseline `000_full_baseline_breaking.sql`). Before a risky migration in production, snapshot first; a tested manual restore procedure (`pg_dump`/`pg_restore`) is in README's "Revenir en arrière après une mise à jour ratée" section.
- **Structured logging** (both modules) via `slog` — JSON in prod / text in dev on the server (`LOG_LEVEL`/`LOG_FORMAT`), text-for-journald by default on the agent. Use `slog.*Context(ctx, ...)` in new code, not the std `log` package or a bare `verbose bool` param.
- **Frontend tests**: Vitest unit/component tests (`npm run test`, `*.spec.ts`) run in happy-dom and run in CI. Real-browser tests (`npm run test:browser`, `*.browser.test.ts`, Chart.js/D3 rendering via Playwright/Chromium) do **not** run in CI — an upstream Vite 8 (rolldown) + Vitest 4 browser-mode bug breaks the dep optimizer (diagnosis in `vitest.browser.config.ts` and in `.github/workflows/ci-frontend.yml`). Run them locally (`npx playwright install --with-deps chromium && npm run test:browser`) before relying on them for a change that touches chart/map rendering.
- **PR titles are enforced, not just a convention.** [pr-checks.yml](.github/workflows/pr-checks.yml) blocks any PR whose title doesn't match Conventional Commits — `<type>(<scope>): <description>` with `type` one of `feat|fix|docs|style|refactor|perf|test|chore|ci|revert|build`, `(scope)` optional. A free-text or auto-generated title (e.g. "Add X") fails this check on open/edit — set a matching title before merging. The same workflow also auto-labels by changed path and warns (non-blocking) past 1000 changed lines.
- **Branching: regular work targets `dev`, never `main` directly.** `main` only moves via a long-lived **release PR** (`dev` → `main`, e.g. #268 `chore(release): merge dev into main — Tabler design system alignment`, or historically just `chore: sync main with dev` — #261) that stays open collecting individual `dev`-targeted PRs and gets merged when a maintainer decides to cut a release. Its body is a `## Summary` grouping the batched changes by theme with links back to the individual PR numbers, plus a `## Test plan` checklist — not a diff dump. There is no CI gate blocking a PR opened directly against `main` (unlike some other projects); the convention is enforced by habit, not tooling. After the release PR merges, a maintainer manually creates and pushes a `vX.Y.Z` tag on `main` — that tag push is what triggers [release.yml](.github/workflows/release.yml) (GHCR image + agent binaries + GitHub Release); there is no automated version-bump workflow. **One exception to "never `main` directly"**: [.github/dependabot.yml](.github/dependabot.yml). GitHub reads that file exclusively from the repository's *default branch* (`main`) to decide what it does — including its own `target-branch` setting — never from `dev`, so a change to it (e.g. #299) has to land on `main` directly to take effect at all; merging it into `dev` only (#297) silently does nothing; `@dependabot recreate` on an existing PR just re-reads the stale config still on `main`.

See [server/CLAUDE.md](server/CLAUDE.md), [agent/CLAUDE.md](agent/CLAUDE.md) and [frontend/CLAUDE.md](frontend/CLAUDE.md) for conventions specific to each module. [AUDIT-2025.md](AUDIT-2025.md) is a point-in-time architecture audit (July 2026) kept for historical reference — its critical/important findings are resolved; don't treat it as current status.

[AUDIT-PRODUIT-2026.md](AUDIT-PRODUIT-2026.md) is the current product-management audit (functional inventory, positioning vs. a Checkmk-like tool, architecture read, risks, open decisions) — unlike AUDIT-2025.md it is not a resolved/historical snapshot, but most of what it originally flagged has since shipped: scheduled-tasks RBAC, maintenance windows, incident ack + escalation, alert correlation/dedup and cross-host rule templates are all closed (ROADMAP.md #1-#5, #9). The two genuinely open Must-have items are a generic Slack/Teams/Discord/webhook channel (#6) and host *groups* derived from tags (#7 — raw `hosts.tags` already exists and is used for filtering; what's missing is grouping and tag-targeted rules). Check ROADMAP.md's status column before treating anything in the audit as an open gap. [ROADMAP.md](ROADMAP.md) is the phased execution plan derived from it — keep its per-item status current when picking up roadmap work instead of letting it drift from the code.
